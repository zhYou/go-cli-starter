# Go CLI 模板目录迁移设计

日期：2026-10-29

状态：用户已于 2026-10-29 确认；实施计划待审阅

关联待办：BL-017

## 意图与范围

用户认为参考仓库的目录组织更合适，已选择“按参考布局迁移”。本次让模板的程序入口、
配置示例、集成测试和开发工具各有明确位置，并同步维护初始化、验证和发布能力。

参考 [project-layout](https://github.com/golang-standards/project-layout) 中的目录职责，
按现有内容建立目录。Go 官方的[模块组织说明](https://go.dev/doc/modules/layout)也介绍了
`cmd` 与 `internal` 的用法。参考布局用于文件组织，业务包继续按当前职责划分。

本次属于跨模块迁移，需要完整设计：入口位置被初始化、故障恢复、构建、进程测试、
MCP 检查和发布配置共同使用。

## 目标与边界

- 程序入口迁入 `cmd/<name>/`；初始化后的目录名与 `--name`、可执行文件名一致。
- 配置示例迁入 `configs/`；真实进程集成测试与共享契约数据迁入 `test/`。
- 单元测试留在各自包中，现有 `internal/`、`tools/`、`docs/` 职责保持清楚。
- 模板改名仍可重复执行、拒绝冲突，并能恢复同版本初始化的中断。
- 命令、选项、JSON、schema、配置优先级、输出流及退出码保持现有行为。
- 源码运行和安装入口明确变更，并提供迁移说明。

本次不新增业务命令、公开库、服务端、部署配置或依赖，不升级工具版本。
`pkg/`、`api/`、`scripts/`、`build/` 等目录在有实际内容时再增加。
GitHub、Codex、mise、GoReleaser 等需要发现的根目录配置保持在当前位置。

需要避免的结果：目录已经移动，但初始化生成不可构建的项目；失败后只恢复文件内容，
留下错误目录；移动契约数据后绕过历史比较；发布包漏掉配置示例。

## 方案比较与选择

| 方案 | 内容 | 取舍 |
| --- | --- | --- |
| 按参考布局迁移 | 入口迁入 `cmd/<name>/`，配置迁入 `configs/`，进程集成测试迁入 `test/` | 分工清楚；源码运行与安装路径变化，需要联动初始化和发布 |
| 保留根入口 | 整理配置和测试目录，保留根目录 `main.go` | 原有根路径运行和安装继续可用；入口位置维持原状 |

用户已选择第一种。命令目录随初始化名称变化、共享契约数据同时归入 `test/`、
发布包保持原有配置文件位置，是本设计提出的实现判断，随本文一起确认。

## 目标结构

`<name>` 表示当前应用名称；原始模板采用原模板名称，初始化后采用用户传入的名称。

```text
.
├── cmd/
│   └── <name>/
│       ├── main.go
│       └── main_test.go
├── configs/
│   └── config.example.yaml
├── internal/
│   ├── apperror/
│   ├── cli/
│   ├── config/
│   ├── contract/
│   ├── greeting/
│   ├── logging/
│   ├── scaffold/
│   └── validation/
├── test/
│   ├── integration/
│   │   ├── process_test.go
│   │   └── testdata/process/*.txtar
│   └── testdata/contracts/
│       ├── initial.json
│       └── v1.json
├── tools/
│   ├── dev/
│   └── init/
├── docs/
├── .github/
├── .codex/
├── go.mod
├── go.sum
├── mise.toml
└── 其他根目录说明与工具配置
```

`cmd/<name>` 继续负责信号、进程退出和版本注入；`internal/cli` 继续负责 Cobra 装配和
输入输出。信号测试依赖入口中的未导出函数，因此随入口移动。
跨进程的黑盒测试从 `internal/cli` 移到 `test/integration`，其脚本跟随测试包。
`tools/` 中是 Go 开发程序，继续通过 mise 从仓库根目录执行。

## 入口发现与路径使用

`internal/scaffold` 统一提供当前应用身份及命令相对路径，供初始化、开发任务、MCP
检查和集成测试使用。继续静态读取 Go 源码，不执行待识别项目的代码。

应用身份保留 `go.mod` 的模块路径和入口 `appName` 常量两个来源。命令候选限于
`cmd/*/main.go`；名称必须通过当前名称校验，且目录名与 `appName` 一致。
入口为 `package main` 并定义主函数。零个或多个符合条件的入口均明确报错，不按遍历顺序
猜测主程序；符号链接和非常规文件按现有路径策略拒绝。
多应用模板不在本次范围内，后续需要时再设计显式主应用标识。

开发构建、模板副本验证、`go list`、schema 验证及进程测试使用发现的命令路径。
GoReleaser 的 `main` 显式指向同一个 `cmd/<name>`，初始化时同步改写。
MCP 检查诊断真实命令入口，不再读取根目录 `main.go`；项目 MCP 启动方式保持现状。
来源提交核验使用迁移后的模板入口路径，不能因路径迁移把派生项目 HEAD 当作模板来源。

源码调用变为：

```sh
mise exec -- go run ./cmd/<name> greet --name Codex
go install <module>/cmd/<name>@latest
```

`mise run build`、`mise run check` 等任务名及 `bin/<name>` 的产物位置保持现有约定。
仓库根目录不保留第二份入口，操作文档同步替换 `go run .` 和根模块安装示例。

## 初始化与目录改名

初始化过程继续受系统锁保护，先恢复旧事务，再读取身份和检查幂等性。
改名涉及两类变化：受管文件内容替换，以及 `cmd/<原模板名>` 到 `cmd/<目标名称>` 的移动。
同名初始化只改模块等必要内容，不执行目录移动。

命令目录移动与内容变更进入同一恢复事务，禁止在事务成功后追加一次无记录的目录改名。
保持同目录临时文件替换和原有权限，事务增加受约束的目录移动记录：

1. 写入前预检源目录、目标目录及全部受管路径。目标目录必须不存在；源命令目录只能含
   受管的入口文件，含额外用户文件、符号链接或非常规内容时明确失败，不修改业务文件。
2. 日志和备份先落盘，再修改源位置的受管文件，然后移动命令目录，最后持久记录提交终态。
   目标名称与路径由已校验参数构造，日志只能描述这一对命令目录。
3. 恢复检查源、目标目录的存在状态与受管文件摘要；根据目录实际所在位置定位文件。
   目录改名与后续日志写入之间中断也必须可识别。两个目录同时存在、两者均缺失、
   文件被人工改动、出现未知内容或参数冲突时保留现场并报错。
4. 未提交事务回滚时先把目录移回源位置，再恢复受管文件内容；已提交事务只继续清理。
   日志清理仍遵循终态最后删除的规则；取消、写入或改名失败都走同一恢复路径。
5. 同参数重试完成恢复后可重新初始化；成功后同参数再次调用返回空变更，来源记录字节不变。
   返回的变更路径反映最终目录，目录移动也纳入变更报告。

事务日志格式升级到 2；`.template-origin.json` 的格式仍为 1。
格式 2 继续覆盖纯内容改写事务。同版本恢复能力必须由故障注入测试证明。
格式 1 日志由原版本工具恢复：新工具发现旧格式时给出中文处理提示并保留现场。
已有项目迁移前须先用旧版本完成或恢复初始化，目录迁移不兼任旧事务转换器。

受管文件清单同步更新迁移路径和新增的应用标识引用。原模板身份常量与测试夹具保持
原模板语义，避免初始化后失去重复调用判断。新目标目录的命令源码、进程测试、构建配置
和使用指南都必须在完整副本验证中检查。

## 配置、发布与机器契约

配置示例源码位置改为 `configs/config.example.yaml`。用户配置目录、`--config` 行为和
配置键保持现状。发布包仍在包根目录放置 `config.example.yaml`，通过 GoReleaser 的文件
映射去掉源码父目录；其[归档文件配置](https://goreleaser.com/customization/package/archives/)
支持 `src`、`dst` 和 `strip_parent`。验证须实际检查六目标归档中的文件，不能只依赖
配置语法检查。二进制命名、版本注入、SBOM、校验清单与来源证明流程延续当前约定。

契约快照从根目录 `testdata/contracts/` 移到 `test/testdata/contracts/`，内容保持不变。
日常检查和更新只使用新路径；`--against` 检查历史 Git 基准时先查新路径，新路径不存在
时再查旧路径。只有两个路径都不存在时才按既有首次基线规则处理，Git 读取故障、引用
错误或非普通文件不能伪装成“没有快照”。历史快照存在但内容损坏时明确失败。
相对基准新增或修改的兼容记录仍按原规则校验。

目录迁移不刷新结果快照，不改变 `schema_version`，也不以兼容记录掩盖 CLI 行为变化。

## 版本与迁移说明

模板版本从 0.1.0 升到 0.2.0，应用发布版本不随模板目录迁移强制改变。
`docs/template-upgrades.md` 增加 0.2.0 的人工迁移步骤，涵盖入口与测试移动、配置位置、
源码安装路径、构建和发布配置、契约历史路径及旧初始化日志处理。
旧项目继续使用原版本时不受影响；新初始化工具不自动升级旧布局项目。

README 增加实际目录说明，开发与兼容性文档同步新路径，AGENTS 中的“根入口”调整为
“程序入口”。历史设计和计划保留当时背景；操作指南使用当前路径。
BL-017 记录设计、实施状态与实际关联 PR，未创建 PR 时明确写“尚未关联”。

## 验证与验收

实施中围绕真实行为验证，不为文件搬移本身编写重复实现的测试：

- 主入口和进程测试迁移后，原有成功、调用失败、配置失败和取消退出行为继续通过。
- 原模板及初始化后的项目都能发现正确入口；无入口、多入口、目录与名称不符均失败。
- 初始化同时改写导入、命令目录和配置，重复调用幂等，冲突拒绝，权限保留。
- 在目录移动前后、文件写入、提交记录和清理阶段注入故障，验证回滚、重试、取消、
  人工修改保护及旧日志提示。命令目标预存在时须在写入前失败。
- 契约检查覆盖迁移前后的 Git 基准，移动数据不触发首次基线回退，不刷新现有快照。
- 模板副本执行测试、构建、schema 与发布配置检查；另以临时安装目录验证
  `go install ./cmd/<name>`，检查初始化后的二进制名称。
- 六目标发布包包含正确二进制、README 和包根目录配置示例；SBOM 与校验清单验证通过。

交付前执行 `mise run fmt`、`mise run check`、`mise run test:race`、
`mise run template:check`、`mise run mcp:check`、`mise run release:snapshot` 和
`mise run release:verify`，并确认 `codex mcp list` 包含 gopls。
`check` 已包含的检查通过一次即可，独立命令只在需要排查或补充验证时重复执行。
本地主机为 Linux；macOS/Windows 的运行结果交由现有 CI 验证，交付时如实报告范围。

目前仅完成调研，`setup` 与 `doctor` 已通过；上述迁移验收尚未执行。
