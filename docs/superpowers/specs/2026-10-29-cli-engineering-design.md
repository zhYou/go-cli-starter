# Go CLI 工程化与基础库设计

日期：2026-10-29。状态：用户已确认。本文用于后续实施规划，设计确认不代表代码已经交付。

实施步骤见[实施计划总览](../plans/2026-10-29-cli-engineering-plan.md)。

## 背景与目标

本项目是主要面向智能体调用、兼顾手动使用、可复制复用的 Go CLI 模板。
当前已有 Cobra 命令树、中文帮助、有类型配置、JSON 输出、固定退出码、
跨平台验证、项目改名和 GoReleaser 发布。此次补充可复用的执行基础，
并把兼容性、安全检查、发布验证和派生项目维护连成完整流程。

用户确定的方向是采用常用库方案：Cobra/pflag、koanf、zap、validator、
Afero、Testify、go-cmp 和 testscript。Schema 采用 Go 类型加 JSON Schema。
Protobuf、Buf 和 ozzo-validation 已从本次范围移出。

成功标准是：新增业务命令可以复用同一套校验、依赖、错误和输出流程；
智能体能够发现调用方式和 JSON 结果结构；维护者能够检查兼容性、依赖风险和发布来源；
派生项目能够识别模板来源、查阅升级指南，并恢复失败的初始化。

### 约束与范围外工作

- 中文仍是项目文档、帮助、日志和错误提示的默认语言。
- 既有命令名、选项、环境变量、JSON 字段和退出码保持兼容。
- 命令只靠参数运行；业务逻辑通过 context 和有类型选项调用。
- 每次调用构造独立命令树和依赖，不增加包级可变配置、命令、日志或校验注册表。
- 继续支持 Linux、macOS、Windows 的 amd64/arm64 发布目标。
- 基础任务在未安装 Codex、RTK 或 superpowers 时仍可运行。
- 本轮不实施业务代码、安装新增依赖、推送、发布或修改托管平台设置。
- 实施范围不包含 TUI、交互提示、分页、应用 MCP 服务、RPC、跨语言 SDK、
  通用依赖注入框架和自动覆盖业务代码的模板同步器。
- BL-001 至 BL-003 继续独立规划；本次不会顺带实施国际化或其他智能体支持。

## 方案比较与选择

### 基础库

方案一保留小型配置和手写校验实现，只为 Schema 和测试引入库，默认依赖较少，
基础能力由模板自行维护。方案二统一引入常用配置、校验、文件系统和测试库，
为派生项目提供现成能力，同时承担适配和升级成本。用户选择方案二，
并明确指定 zap 和 validator。

### Schema

| 方案 | 收益与代价 | 结论 |
| --- | --- | --- |
| Go 类型与当前命令描述 | 延续当前实现，结果结构仍需查阅文档或示例 | 保留现有能力，继续扩展 |
| Go 类型与 JSON Schema | 与现有 JSON 输出衔接，结果结构可发现、可验证，需要处理序列化语义和补充描述 | 用户已选择 |
| Protobuf 与 Buf | 适合共享 IDL、多语言生成和协议管理，需要代码生成工具链和 JSON 适配 | 本次不采用 |

用户已确认采用 `github.com/google/jsonschema-go`，用于类型推导和测试中的结果验证。
该库由 Go 团队成员开发，以 Google 官方开源项目的独立 Go 模块发布，未纳入标准库。
运行时无需额外第三方依赖；具体版本在实施前核验稳定标签并锁定。
参考：[库说明](https://github.com/google/jsonschema-go)、
[Go 团队成员的发布介绍](https://opensource.googleblog.com/2026/01/a-json-schema-package-for-go.html)。

## 命令执行与依赖

### 构造与职责

根进程入口继续负责信号和退出，`internal/cli` 负责参数适配、命令树和输入输出。
拆出独立命令构造函数，例如 `newGreetCommand` 和 `newVersionCommand`。
根构造函数只组织公共选项、执行准备和命令注册。

每次调用创建依赖对象，显式传入 IO、配置加载器、logger、校验入口和业务函数。
业务包继续使用有类型 Options/Result，不接收 Cobra 命令对象。
命令测试能够替换业务函数，直接验证参数转换、调用次数、错误映射和输出。
依赖以构造参数、函数和小接口表达，具体接口名称由实施者决定。

调用顺序为：解析参数并校验，加载配置，创建本次 logger，调用业务，
完整渲染结果，写出结果，清理资源并映射退出码。
帮助、版本、补全和 schema 继续绕过配置加载，并保持已有输出形式。

### 错误分类

增加可通过 `errors.As` 识别的项目错误类型，至少区分调用无效、配置失败和运行失败。
包装保留原因链，`errors.Is` 仍能识别 context 取消和超时。
业务错误的退出码来自明确分类，不依赖业务执行到哪个 hook。
Cobra 的未知命令、解析、必填标记和其他参数校验失败统一在适配层归入调用无效。
框架错误适配方式由实施者选择，但必须覆盖这些来源。

退出码保持 0 成功、1 配置或运行失败、2 调用无效、130 取消。
沿用当前实现对 `context.DeadlineExceeded` 的 130 映射。
尚未分类的业务错误按运行失败处理。错误默认仍以中文文本写 stderr，
不新增 JSON 错误协议，也不要求调用者解析错误文案决定退出码。

### 统一输出

为业务命令提供公共 JSON 和文本输出入口。业务计算和渲染完成后才写 stdout；
JSON 完成序列化后写出一个文档并附加一个换行，文本渲染失败时不写部分结果。
写入错误和短写均返回运行失败。帮助仍为文本，补全仍为原生脚本，schema 始终为 JSON。

参数、配置、业务和序列化失败时 stdout 为空。输出设备写入失败时可能已有部分字节，
进程无法撤回这些字节；消费方必须先检查退出码。本文作者提议据此精确化现有文档的
“命令失败时 stdout 为空”约定，不承诺操作系统写入的事务性。

## 配置、日志与校验

### koanf

保留有类型 Config 和加载入口，在其内部使用独立 koanf 实例装配来源。
只引入实际需要的 provider/parser。对外不暴露随处读取配置键的可变对象。

覆盖顺序继续为显式选项 > 非空环境变量 > YAML > 默认值。
读取 flag 时必须先检查 `Changed`；显式传入默认值也必须覆盖低优先级来源。
默认配置文件不存在可以忽略，显式路径不存在、未知键、类型错误、多文档 YAML
和无效枚举值仍须失败。保留现有对空环境变量和大小写归一化的行为。

koanf 的来源合并、YAML 解析与有类型解码之间增加必要的严格校验，
不能因更换配置库而放宽已有行为。具体 parser 由实施者选择并验证这些条件。

### zap

每次调用创建 zap logger 并注入，不替换全局 logger。
日志写入传入的 ErrOut，默认使用 console 编码，等级仍为 debug/info/warn/error，
默认 warn；帮助等发现命令不因日志配置损坏而失败。
项目日志消息使用中文，日志字段名保持稳定。
不默认记录完整参数、环境或配置值；业务包按需要记录经过筛选的字段。
logger 清理不能关闭调用者提供的输出流，也不能用清理错误覆盖原始命令错误。

### validator

Options 的约束由统一校验入口执行：常见字段规则使用标签，复杂条件使用注册的 Go 回调。
CLI 在执行前调用同一套校验，业务入口也保证直接调用时输入有效。
校验器在使用前完成注册，经依赖注入复用，不在业务执行中修改共享规则。
校验失败转换为项目错误，提供中文提示和明确的选项上下文。
复用业务规则，避免 CLI、业务包和帮助各维护一份独立判定。

运行时校验与公开结构描述分别承担职责。validator 的自定义 Go 逻辑不自动翻译为
JSON Schema；本期只导出 Cobra 已明确提供的调用信息和结果类型信息。

## 命令发现、结果 Schema 与兼容性

### 定义来源

- Cobra 命令树提供命令路径、帮助、示例、参数类型、必填标记、默认值和继承关系。
- 业务 Result 的 Go 类型及 JSON 标签提供成功结果结构。
- 每条业务命令在构造时注册结果类型及必要的描述，注册表属于本次命令树。
- Schema 生成只读取类型和元数据，不执行业务、不读取用户配置、不请求网络。

先为 `greet` 和 `version` 注册结果类型，新增业务 JSON 命令必须遵循同一约定。
帮助和补全不注册 JSON 业务结果。schema 自身继续由固定命令描述契约和测试保障，
本期不要求它递归提供自身的结果 Schema。

### 输出扩展

保持 schema 当前所有字段及 `schema_version: 1`，在拥有业务 JSON 结果的命令描述中
新增可选 `result_schema`，内容为 JSON Schema Draft 2020-12。
现有消费者应忽略未知描述字段；此次增加属于本文明确允许的向后兼容扩展。
命令树仍从 Cobra 生成，不维护第二份命令清单。

Result 是结果契约的定义源。字段描述可通过库支持的标签补充。
`omitempty`、指针、空切片、map、嵌套类型及自定义 JSON 编码必须与实际输出一致；
无法正确推导的类型显式提供覆盖，无法描述时返回清晰错误，禁止静默丢字段。
所选库不会自动推导递归 Go 类型，这类结果需显式描述；其验证器将 format 作为描述信息，
不据此检查邮箱或日期等格式。需要保证的格式约束由显式校验和对应测试覆盖。
结果对象允许将来增加字段，生成的对象 Schema 应允许额外属性；已定义字段的类型、
可空性和必填约束须精确。该策略与拒绝未知配置键的策略分别处理。

`schema greet` 返回的对应命令描述会包含 message 字段为必填字符串的结果结构。
每个 JSON 结果样例均需通过其公开 Schema 验证。
参考：[JSON Schema 的职责](https://json-schema.org/overview/what-is-jsonschema)。

### 兼容性规则与基线

将发布过的命令名、选项、机器字段、枚举、退出码和结果类型视为公开接口。
命令和描述可以增加可选信息，消费者应容忍未知字段。
删除或重命名接口、改变字段类型、把原本保证存在的结果字段改为可缺省、
使已有合法调用失败，都必须作为不兼容变更规划，并提供版本和迁移说明。
帮助及错误文案可以修订，但退出码和机器接口不以文案匹配实现。

建立提交到仓库的机器接口基线，使用规范化的命令描述、结果结构和代表性结果。
首次基线来自改造前的当前行为；允许新增 `result_schema` 的扩展单独记录。
检查既验证实际输出，也检查基线差异；变更不能靠重新生成快照自动通过。
新增兼容字段可以在审查说明中更新基线，不兼容变更必须附迁移说明并按版本策略处理。
本期不实现能证明任意两个 JSON Schema 相互兼容的通用推理器。

## 初始化与文件操作

引入 Afero，为文件操作提供可替换实现和故障注入入口。
真实执行保留原有根目录解析、受管白名单、常规文件和符号链接检查。
内存文件系统用于受控失败测试，真实文件系统测试负责权限、路径和各平台行为。
Afero 本身不承担多文件事务。

初始化采用“预检、准备、应用、完成”四个阶段：

1. 校验参数、当前身份、受管路径和全部可预期内容；准备所有目标数据。
2. 在根目录下的专用临时目录保存原文件、权限和恢复记录；完整准备后才改写受管文件。
3. 按记录逐个应用；普通写入失败时尝试回滚。回滚失败保留恢复资料并报告位置。
4. 全部成功后确认目标身份，写入模板来源信息，再清理恢复目录。

恢复记录需含事务格式版本、原/目标身份、受管相对路径以及原/目标内容摘要。
下一次初始化先检查未完成记录，再判断项目身份，避免部分改名导致无法重试。
仅相同目标参数允许自动恢复：在确认文件仍匹配原内容或预期目标内容后回滚到原状态，
然后重新开始。参数冲突、摘要不匹配或人工修改时停止并保留资料，不能覆盖用户修改。
恢复记录中的路径也须通过根目录、白名单和符号链接检查。
通过专用目录的排他创建阻止同时初始化；留下的记录按恢复流程处理。

该保证覆盖可识别的写入失败和中断后的恢复，不承诺所有文件系统上的断电事务性。
临时资料排除在模板复制和发布产物之外，恢复测试必须覆盖失败与重试。

## 安全与依赖维护

### 持续漏洞检查

在 mise 中锁定 govulncheck，提供独立 `mise run vuln`，检查整个模块并对命中返回失败。
PR/main CI 和定时任务执行该检查；定时检查覆盖代码未变但数据库新增漏洞的情况。
网络或数据库不可达属于检查失败，不能报告为无漏洞。
基础 `check` 保持源码检查入口，联网漏洞检查由独立任务和 CI job 组合，
避免把无网络的源码检查与数据库访问混为一谈。
参考：[Go 漏洞检查](https://go.dev/doc/security/vuln/)。

### 版本一致性与自动更新

增加 `mise run versions:check` 并接入 `check`。
以 mise.toml 的精确工具版本作为项目工具版本依据，检查 mise.lock 的六个平台、
Go 模块最低版本与 toolchain、doctor、CI 引导版本和文档版本是否符合明确关系。
Go 最低版本、工具链补丁版和 mise 最低版本分别比较，不能要求无差别字符串相等。
用语义化版本解析检查版本，避免当前包含字符串的宽松匹配。

新增 Renovate 配置覆盖 Go 模块、Actions SHA 和 mise 工具，排除预发布版，
相关工具链变更分组提交。默认由维护者审查合并，版本一致性检查是必需检查。
Renovate 只能在平台启用后运行；仅配置文件存在不代表已经启用。
锁文件更新所需的平台能力按官方机制配置，不能假设文档和 doctor 会自动同步。
参考：[Renovate 对 mise 的支持](https://docs.renovatebot.com/modules/manager/mise/)。

所有新增 Go 库与工具在实施前核验官方最新 LTS 或稳定版并锁定具体版本，
记录来源与兼容性；本设计不把讨论期间的版本号当作实施时的最新版。
新增应用标识所在文件同步进入受管白名单。

## 发布

继续使用六目标纯 Go 产物、现有压缩格式、版本注入和校验文件。
在 GoReleaser 中为每个发布压缩包生成独立 SPDX JSON SBOM，并将 SBOM 纳入校验清单。
作者提议使用官方集成的 Syft，版本及六平台安装方式在实施时锁定；
显式使用本地文件分析，snapshot 生成 SBOM 不依赖发布凭据或外部包元数据补全。
参考：[GoReleaser SBOM 配置](https://goreleaser.com/customization/sbom/)。

发布 workflow 为最终压缩包及 SBOM 生成 GitHub 构建来源证明。
只在 release job 配置必要的 contents、id-token 和 attestations 权限。
PR/main 检查保持只读；普通本地构建、测试和 snapshot 不生成托管平台证明。
Release 文档提供校验文件、SBOM 和 `gh attestation verify` 的验证步骤。
托管证明需要目标仓库和 GitHub 套餐支持；文档说明私有仓库的前提，
不能把本地 snapshot 通过表述为远端证明已验证。
参考：[GitHub 构建来源证明](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)。

本轮和后续实现验证使用 snapshot，不创建远端 Release、推送标签或发布产物。
实际发布仍由目标项目维护者按既有标签流程触发。

## 协作与模板升级

复用现有开发说明，增加 PR 模板、SECURITY.md、维护责任说明和仓库初始化清单。
清单涵盖责任人、私密安全报告入口、必需检查、分支/标签规则及 Renovate 启用步骤。
这些是需要维护者设置的托管状态，本项目不自动修改目标仓库设置。

## 实施顺序与交付边界

设计确认后再编写实施计划，建议按依赖关系分为四批：

1. 命令构造、错误、输出、koanf、zap 和 validator，先用现有行为测试保护兼容性。
2. 结果 Schema、机器接口基线、go-cmp 与真实进程测试。
3. Afero、初始化恢复、来源元数据和迁移说明，验证复制后的独立项目。
4. 版本检查、漏洞检查、依赖更新配置、协作入口、SBOM 和来源证明配置。

每批保持可独立验证，但只有十三项均完成验收，才能宣称本轮实施完成。
本轮设计文档的完成不代表上述能力已经实施或测试通过。
